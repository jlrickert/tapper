# Commands

Build, test, lint, and install. [Development](README.md) is this section's
index.

## Build And Test

```bash
# Build
go build ./cmd/tap

# Test
go test ./...                              # all tests
go test ./pkg/keg/... -v                   # single package, verbose
go test ./pkg/keg -run TestConcurrentCreate # single test by name
go test -race ./pkg/keg/...               # with race detector

# Cached test run of ./pkg/... (requires go-task)
task test
```

## Lint

```bash
go vet ./...
task lint:docs                            # exported interface documentation
task lint:fs                              # Runtime filesystem discipline
```

### Stable interface documentation

Every exported interface declared under `pkg/...` and every exported method it
declares must have an adjacent Go doc comment beginning with the declared
identifier. Deprecated methods still require their contract documentation and
a standard `Deprecated:` paragraph. `task lint:docs` enforces this rule without
a baseline or suppression list and runs explicitly in CI.

`task lint:fs` enforces the filesystem half of the
[Runtime Abstraction Rule](../architecture/runtime-and-concurrency.md#runtime-abstraction-rule).

## Installing Binaries

**A development build of `tap` is never installed on the host machine.** Not
`go install ./cmd/tap`, not `task install-tap`, not a `go build -o` into a
directory on `PATH`.

The reason is that nothing about such an install is scoped to the work you are
doing. The Claude Code plugin's MCP server is defined as `{"command": "tap",
"args": ["mcp"]}`, so it runs whatever `tap` resolves on `PATH`: one install
silently changes the binary behind every agent session, every integration, and
every KEG on that machine, and it keeps doing so long after the session that
installed it ended. A development build is also unversioned against the Hub —
`tap version dev` says nothing about which API contract it speaks. A `dev`
binary that predated the `Tapper-API-Version` request header left every agent
session on a machine failing with `400 Bad Request: send Tapper-API-Version`,
and neither reconnecting the MCP server nor reloading plugins could fix it,
because neither touches the binary. The plugin directory under
`~/.local/share/tapper/integrations/claude` is generated by whichever `tap` ran
`tap integrate`, and that binary stamps its own version into every plugin
manifest it extracts — the rendered tree in the repository carries only a
`0.0.0-dev` placeholder. A build from a developer checkout therefore installs
plugins reporting `0.0.0-dev`, which is what Claude Code reads as its update
gate.

Instead:

- **Hosts run released builds**: `brew install jlrickert/formulae/tapper`.
- **Unstable builds are tested in a container.** `task sandbox:shell` gives an
  isolated Ubuntu container that builds from the bind-mounted source and
  behaves like a vanilla machine — see [the sandbox README](../../test-env/README.md).
  It builds and runs `tap` inside the container, so the host `PATH` is never
  touched.
- **`task install-tap` is a human-run command.** It runs `go install ./cmd/tap`
  and replaces the `tap` on the host `PATH`. It exists for a person to run
  deliberately, accepting what it replaces. An agent never runs it and never
  offers to run it.

Building a throwaway binary to a scratch directory and invoking it by full path
is not an install and is fine — it is how you verify a source change against a
real Hub without altering what anything else resolves.
